# benchmarks/ · 性能证据

> 这里是从 CI 产物目录里**原样搬过来**的 8 份性能基准输出。
> 它们是这套流水线「性能层判据」的原始证据 —— 不是我事后跑的 demo。

---

## 一、为什么只有 8 份（以及为什么没搬别的）

CI 的产物目录（`logs/ci/`）里还有 `diff-*` / `snapshot-*` / `live-backup-*` /
`apply-*` / `cm-*` —— **一个都没搬**，因为它们可能包含内部信息
（线上对象快照、ConfigMap 全文、diff 里的内部值）。

**只搬了 `bench-*.txt`** —— 它们的输出格式是固定的（见下），
不含任何配置或凭据。

---

## 二、输出格式是**故意固定**的

`verify.sh` 用 `grep` 从里面提取数值，所以格式不能随便改：

```bash
# bench.py（生成式 LLM）
VAL=$(grep -oE '平均 tok/s  = [0-9.]+' "$BENCH_OUT" | grep -oE '[0-9.]+')

# bench-embed.py（向量服务）
VAL=$(grep -oE '平均 req/s  = [0-9.]+' "$BENCH_OUT" | grep -oE '[0-9.]+')
```

→ **改 `bench*.py` 的输出格式会静默让判据失效**（`VAL` 变成 `0`，然后"性能不达标"）。

> 这是"脚本即判据"的一个代价：**判据依赖了输出格式这个隐式接口**。
> 更稳的做法是让 bench 直接输出 JSON 并判退出码。

- `bench-10.txt` … `bench-18.txt` —— 早期手写序号（**10/11/17/18 是 Jenkins 构建号**）

  `bench-$(date +%Y%m%d-%H%M%S).txt`）

## 四、⭐ 测量纪律（看这些数字前必须知道的事）

### （1）预热 3 次不计入

```python
WARMUP = 3      # bench.py / bench-embed.py
ROUNDS = 10     # bench.py（tok/s）
ROUNDS = 20     # bench-embed.py（req/s）
```

第一次请求包含 KV cache 分配、CUDA kernel 预热、Python 模块懒加载 ——
**不预热的话第一批数字没有意义**。
`bench-20261008-121737.txt` 里第一次预热是 **43.62 ms**，之后立刻降到 ~8 ms
—— 这就是预热要解决的问题。

### （2）只有同 session 的 A/B 才能比较

跨 session 比较**不可靠**，因为至少三个变量会变：

| 变量 | 影响 |
|---|---|
| GPU 上还有没有别的服务 | march7 缩到 0 副本前后，实测吞吐会变 |
| 显存余量 / KV cache 实际大小 | `--kv-cache-memory` 是显式的，但 CUDA context 不是 |
| 宿主的 CPU/IO 争用 | 这是**一台同时在干别的事的机器**，不是隔离的 benchmark 环境 |

**所以本仓库不做「改动前 vs 改动后」的结论** —— 除非是同一次 session 里
前后紧挨着跑的两组。`bench-17`（152.7）和 `bench-18`（160.3）相差 5%，
**不足以支持任何"优化生效了"的结论**，它们只是两次独立观测。

### （3）已知的一次测量异常（保留，不隐藏）

`bench-20261008-121118.txt`：

```
预热3:  64 tok / -0.66s =  -96.7 tok/s
```

**负耗时。** `time.time()` 在跨核/虚拟机时钟下**非单调**导致 ——
`t1 - t0` 算出负数。

- 它落在**预热**阶段（不计入结果），所以那次的 `平均 tok/s = 141.8` 仍然有效
- **但如果出现在正式轮次里，就该先怀疑测量，而不是服务**
- 更稳的修法是 `time.monotonic()`（单调时钟）。⚠️ **本仓库的 `bench.py` 用的是
  `time.time()`，这个改进没有做** —— 记在这里

### （4）这些数字测的是【单流】，不是吞吐上限

`bench.py` 是**串行**发请求。它证明的是「单条请求的生成速度没有退化」，
**不证明**「服务能扛并发」。

并发 64、显存压力下、长上下文下的行为 —— **都不在判据内**。
（CPU/内存的 `limits` 是按并发 8/16/32 的 cgroup 实测定的，但那是**资源**判据。）

见 [docs/06 · 假设 2](../docs/06-limitations.md)。

### （5）性能层是三层里唯一的**环境相关**判据

日志层和功能层是**确定性**的（同样的输入 → 同样的结论）。
性能层不是 —— 它依赖当时机器上还有谁在干活。

**这就是为什么门槛（100 / 20）留了 1.4×–5.7× 的余量**：
不是为了"宽松"，是为了**不因为邻居抖动而误触发自动回滚**。

## 五、怎么重新跑

```bash
# 完整三层（含性能层，会自动写一份新的 bench-<ts>.txt）
./ci/scripts/verify.sh

# 只跑性能层
./ci/scripts/verify.sh --layer=bench

# 提高门槛（默认 100 tok/s / 20 req/s）
BENCH_MIN=120 ./ci/scripts/verify.sh

# 单独用基准脚本（不判通过/失败）
CI_TARGET=march7 python3 ci/scripts/bench.py
CI_TARGET=embed  python3 ci/scripts/bench-embed.py

# 显式指定端点（默认自动探测，见 ci/scripts/endpoint.py）
VLLM_URL=http://<WSL-IP>:30800 python3 ci/scripts/bench.py
```
